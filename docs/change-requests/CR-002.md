# CR-002 — TRS §5.3 toolchain moves Java 17 → Java 21 LTS

- **Status:** **ACCEPTED** — owner ruling at the WP-02 S4b review, 2026-08-19.
- **Raised:** 2026-08-18, PR #15 §3, by the implementing agent.
- **Execution:** **EXECUTED in WP-02 slice S5**, 2026-08-19. See Sec. "What executing this CR involved" below for what actually moved.
- **Affected requirements:** TRS §5.3 (pinned toolchain), TRS-CICD-006
- **Affected gate:** **G-06** — the Lazysodium 5.1.0 alignment blocker is CLEARED. G-06 itself remains `unproven_owner`: it is a store-submission gate and no agent may advance it.

## Change

TRS §5.3 pins the Java toolchain at 17. It moves to **Java 21 LTS**, so that
Lazysodium **5.2.0** can be adopted.

## Rationale (owner text)

Lazysodium 5.2.0 ships **16 KB page-aligned** native libraries; 5.1.0 does not.
Google Play's 16 KB requirement makes that a **G-06 blocker** on 5.1.0 — an
Android 15 device with 16 KB pages cannot map 5.1.0's `arm64-v8a/libsodium.so`
at all. The library is held at 5.1.0 today only because 5.2.0 ships class-file
65 bytecode, which javac under the Java 17 toolchain refuses outright, so the
alignment fix and the toolchain move arrive together or not at all.

**Direct libsodium JNI remains the recorded fallback** if the toolchain move
proves worse than expected.

## What executing this CR involved (S5, 2026-08-19)

- TRS §5.3 toolchain value and `tools/toolchain/toolchain-manifest.json`.
- `gradle/libs.versions.toml`: `lazysodium` 5.1.0 → 5.2.0; the Java 17 pin
  comment at the Checkstyle entry is unrelated and stays (Checkstyle 13.x is a
  separate hold, see below).
- Removal of the narrow `Aligned16KB` lint disable in
  `android-app/app/build.gradle.kts`, with its rationale comment.
- **Checkstyle**: pinned at 12.3.1 because 13.x refuses JVM 17. Java 21 removes
  that constraint, but raising Checkstyle is a separate decision and is not part
  of this CR.
- Re-running the instrumented suite: the binding changes underneath
  `LibsodiumRecoveryCrypto.java`, which is the only file that imports it.

## What was done, and what was proven

- **Toolchain to Java 21 LTS** (Temurin 21.0.12+8): the `:protocol-conformance`
  Gradle toolchain, five `setup-java` pins across both workflows, and
  `tools/toolchain/toolchain-manifest.json`.
- **Lazysodium 5.1.0 → 5.2.0**, pinned in the catalogue, sha256 recorded, the
  MPL-2.0 notice the APK ships re-versioned. The owner's five adoption
  conditions are unchanged and still hold: unmodified use, the licence text in
  the shipped notices, an SBOM entry, one importing file, and a direct libsodium
  JNI binding rather than a fork if patching ever becomes necessary.
- **The `Aligned16KB` lint disable is deleted.** The check is live and passing.
- **The alignment was verified from the artefacts, not the release notes.**
  Every PT_LOAD segment of both 64-bit objects in 5.2.0 has `p_align` `0x4000`;
  the same segments in 5.1.0 have `0x1000`. That is the defect, measured.
- **The crypto surface is unchanged**, proven by re-executing the cross-language
  recovery vectors on an emulator against 5.2.0 rather than by reading notes.

## What this CR deliberately did NOT do

- **Checkstyle stays at 12.3.1.** The Java 17 JVM was the only thing blocking
  13.x and Java 21 removes it, but this CR says raising Checkstyle is a separate
  decision. Deferred to WP-03.
- **The Android module still compiles to Java 17 language level.** CR-002 needed
  a javac that can READ bytecode 65, which is a property of the JDK. Raising
  what the app EMITS puts class file 65 through D8 and desugaring at minSdk 26
  for no language feature anybody uses. Deferred to WP-03.
- **No WP-03 wiring.** `LibsodiumRecoveryCrypto` is the only file that imports
  the binding and it did not need a line changed.
