# CR-004: A per-device send rate limit for the relay

- **Status:** **PROPOSED**, awaiting the owner's ruling.
- **Raised:** 2026-11-22, in WP-05 S5b, by the implementing agent
  (TRS-CONST-003: a new register value needs an approved change request).
- **Register entry (new):** `sessions_remote_text.RELAY_SEND_RATE_PER_MIN`
- **Error registry (new):** `ERR_RELAY_RATE_LIMITED`
- **Affected requirements:** TRS-BCK-004 ("the relay shall enforce TTL
  deletion, quotas, **rate limits**, size limits and idempotency"),
  SRS-SAF-006 (rate-limit relay packets), SRS-NFR-SCL-003 (rate limits
  configurable by environment), TRS-BCK-008 (rate limits live in Redis).
- **ADRs:** ADR-004 (every tunable value comes from the register), ADR-006
  (override bounds).
- **Executes:** WP-05, the slice after S5b.

## Why this is a change request

TRS-BCK-004 requires relay rate limits, but the register (TRS §23.2) gives the
relay a TTL, a size limit and a mailbox quota and **no rate**. ADR-004 forbids
inventing the number in code, so the value must enter the register first, and
the register is frozen (TRS-CONST-003). Everything else TRS-BCK-004 asks for is
built and tested; this is the one piece that waits on a number.

## Proposed register entry

```json
"RELAY_SEND_RATE_PER_MIN": {
  "default": 120, "min": 30, "max": 600, "overridable": true,
  "notes": "Per sending device; envelopes submitted per fixed one-minute window, receipts and retries included.",
  "anchors": ["TRS-BCK-004", "SRS-SAF-006", "SRS-NFR-SCL-003"],
  "source": "CR-004"
}
```

### Why these numbers

- **Default 120 per minute.** In a lively conversation a person sends roughly
  20 texts a minute. Their phone also sends a delivery and a read receipt for
  each message it receives, which is about 40 more, and retries after a weak
  signal can double a burst. That is about 60 to 80 a minute at the busy end,
  so 120 leaves headroom and no real user should ever hit it. A flooding script
  sending thousands a minute is cut to 2 a second.
- **Minimum 30.** Below this, the receipts of an active chat alone could trip
  the limit.
- **Maximum 600** (10 a second). Above this, the limit no longer protects the
  relay from one misbehaving device.

## Proposed error code

`ERR_RELAY_RATE_LIMITED`, numeric 163, category backend. The phone treats it
like `ERR_RELAY_MAILBOX_FULL`: the message stays queued and is retried after
the window, which the response states in a `Retry-After` header. User message:
"Sending too fast. Your messages will go out in a moment."

## How it would work

A fixed one-minute window per sending device, counted in Redis with one atomic
increment and an expiry (TRS-BCK-008). The counter key holds the device's
routing id and a count, and nothing about recipients or content
(TRS-BCK-002). The check runs before any capability lookup, so a rate-limited
sender learns nothing about whether a recipient has blocked them (SRS-MAT-003).

## What it does not cover

Rate limits for interest requests already exist (`INTEREST_RATE_LIMIT_PER_HOUR`)
and venue room posts have their own (`VENUE_ROOM_POST_RATE_PER_MIN`). Gateway
and WAF limits (TRS-BCK-010) are infrastructure, configured in WP-05 S8. This CR
is the relay's own per-device send limit only.
