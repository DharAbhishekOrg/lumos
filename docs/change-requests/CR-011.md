# CR-011: HELLO v2 and the local link key (ADR-015, option C)

- **Status:** **PROPOSED** by the agent on 2026-11-28. Needs the owner's acceptance before any register edit (TRS-CONST-003).
- **Executes:** the ADR-015 slice. The register change, the codegen (Go, Java, Swift) and every regenerated golden vector land in one commit, with the Go reference and its known-answer vectors. Java and Swift follow, each checked against those vectors.
- **Raised:** 2026-11-28 by the agent, after the owner chose option C in [ADR-015](../adrs/ADR-015-local-link-encryption.md).
- **Affected requirements:**
  - TRS-PROTO-003 (the full frame header is AEAD associated data);
  - TRS-PROTO-017 (trust only at the authenticated HELLO);
  - TRS-CRY-001 (the approved suite), TRS-CRY-011 (nonces never repeat under a key), TRS-CRY-013 (one stable error for every AEAD failure), TRS-CRY-014 (domain separation);
  - SRS-PRO-002/003/007, SRS-MAT-001/004, SRS-NFR-PRI-002 (previews and interest are private to the two people);
  - TRS-CONST-003 (a register change needs an approved CR);
  - G-07 (cryptographic review, the owner's gate; not advanced by this CR).

## The change, in one paragraph

Each phone makes a fresh X25519 key pair for every link and puts the public half in its HELLO and HELLO_ACK. Its own ACK signature covers that key. When both handshakes finish, both phones compute the same pair of link keys from three Diffie-Hellman results and the exact bytes of all four handshake messages. Every frame after the handshake is ChaCha20-Poly1305 encrypted, with the full frame header as associated data and the nonce taken from the header's sequence number. The ephemeral private keys and the link keys are wiped when the link closes, so a recording of the radio cannot be decrypted later, even with a stolen phone.

## New register values

All in `crypto_protocol`, all frozen (not overridable by signed configuration).

| Name | Value | Why |
| --- | --- | --- |
| `HELLO_V2_LAYOUT` | the v1 fields in the v1 order, then `eph_public_len` 32 after `binding_sig`, before `nonce`; `hello_version` = 2; `total_len` 196 | Carries the per-link ephemeral X25519 public key |
| `HELLO_ACK_V2_LAYOUT` | hello_v2 fields, then `auth_sig_len` 64; `total_len` 260 | The ACK signature (same rule as v1) now covers the sender's ephemeral key |
| `LINK_TRANSCRIPT_INFO` | `lumos/link/transcript/v1` | Domain prefix of the transcript hash (the HKDF salt) |
| `LINK_KEY_KDF_INFO` | `lumos/link/key/v1` | HKDF-SHA-256 info for the two per-direction link keys |
| `LINK_AEAD_NONCE_LAYOUT` | `zero_prefix_len` 8, `sequence_len` 4, `total_len` 12 | The 12-byte ChaCha20-Poly1305 nonce: 8 zero bytes, then the frame header's `sequence` (u32, big-endian) |

Nothing else moves: no new error code (failures use the existing `ERR_CRYPTO_AEAD_AUTH_FAILED` and `ERR_CRYPTO_REPLAY`), no new dependency, and `PROTOCOL_VERSION` stays 1.0 (see "One choice for the owner" below).

## The rules the register values serve

### 1. The ephemeral key
- A new X25519 key pair per link, from the platform's secure random source. It is never stored, never logged and never reused on another link.
- The same ephemeral public key goes in the phone's HELLO and its HELLO_ACK on that link. A peer whose ACK carries a different ephemeral key from its HELLO is dropped (fails closed).
- It is authenticated by the sender's own ACK signature, which covers every ACK byte before the signature. The peer's ACK also covers the SHA-256 of our HELLO, so a relayed or swapped key breaks a signature.

### 2. Ordering the two sides
- "Lower" and "higher" are the two phones ordered by their peer identifiers (PEER_ID_KDF_INFO), compared byte by byte. Both phones compute the same order without talking.

### 3. The transcript (the salt)
- `salt = SHA-256( UTF-8(LINK_TRANSCRIPT_INFO) | hello_lower | ack_lower | hello_higher | ack_higher )`
- Each item is the exact payload bytes that side sent (196 or 260 bytes), not a re-encoding.

### 4. The key material
- `DH1 = X25519(eph_lower, eph_higher)`
- `DH2 = X25519(identity_dh_lower, eph_higher)`
- `DH3 = X25519(eph_lower, identity_dh_higher)`
- `ikm = X3DH_F_PREFIX (32 × 0xFF) | DH1 | DH2 | DH3` (the existing register value, same domain-separation idea as X3DH)
- Any DH result of all zeros (a low-order point) fails closed; nothing is derived.
- `okm = HKDF-SHA-256(salt, ikm, info = UTF-8(LINK_KEY_KDF_INFO), length 64)`
- `key_lower_to_higher = okm[0:32]`, `key_higher_to_lower = okm[32:64]`
- `ikm`, `okm` and all DH results are wiped right after use. The ephemeral private key is wiped once the keys exist.

### 5. Every frame after the handshake
- HELLO (0x01) and HELLO_ACK (0x02) are the only plaintext frames on a v2 link.
- Payload = ChaCha20-Poly1305(key for this direction, nonce, plaintext, associated data = the full encoded frame header) (TRS-PROTO-003).
- Nonce = 8 zero bytes | header `sequence` (u32, big-endian).
- The sender's `sequence` starts at 0 for the first encrypted frame in its direction and goes up by one for each frame. It never repeats under a key (TRS-CRY-011). At 2³²−1 the link is closed rather than wrapped.
- The receiver accepts a frame only if its `sequence` is greater than the last one it accepted in that direction; anything else is `ERR_CRYPTO_REPLAY` and is dropped. Every AEAD failure is the one stable `ERR_CRYPTO_AEAD_AUTH_FAILED`, with no detail (TRS-CRY-013), and closes the link.
- Encryption happens before fragmentation; the receiver decrypts after reassembly.

### 6. Older phones
- A phone that speaks HELLO v1 can still appear as a card (the v1 rules, unchanged), but it is never sent a preview, an interest request or anything after HELLO.
- Downgrade: a v2 phone always sends v2. An attacker cannot turn a v2 exchange into v1 without breaking the ACK signatures, because each ACK covers the hash of the exact HELLO it answers.

## Known-answer vectors (with the Go reference)

- Fixed identity and ephemeral keys for two sides; the four handshake payloads; the salt; DH1–DH3; both link keys.
- One encrypted frame each way (sequence 0 and 1), header and ciphertext.
- Negative cases: a tampered header byte, a repeated sequence, a lower sequence, a mismatched ephemeral key between HELLO and ACK, an all-zero DH result, a v1 peer.
- Java and Swift must reproduce every vector byte for byte.

## One choice for the owner

ADR-015 mentioned "a protocol version bump". This CR proposes **not** moving `PROTOCOL_VERSION` (it stays 1.0, encoded 16), and putting the change in `hello_version` (1 → 2) instead.
- Why: the frame header format does not change; only what follows HELLO on a local link does, and that is decided per link by the HELLO version.
- Moving `PROTOCOL_VERSION` would change every frame vector for no wire benefit.
- If the owner prefers the bump anyway, it would be 1.1 (encoded 17); a minor change does not fail closed.

## What does not change

- The advertisement, the EID schedule, the GATT layout (CR-010) and the handshake timeout.
- The relay path and its end-to-end encryption (X3DH and the Double Ratchet).
- Every safety rule. Nothing about a person is added to HELLO: the ephemeral key is random and per link, so it cannot track anyone.

## Safety, privacy and legal impact

- **Privacy (GDPR Article 9):** previews can carry gender identity, orientation and a bio. With this CR they are unreadable to anyone listening on the radio, including someone who later steals one of the two phones (forward secrecy).
- **Safety:** for LGBTQ people in hostile places, a sniffed orientation field next to a key is real-world danger. This removes that exposure on the local link.
- **No new data** about anyone is created, kept or sent. No backend, analytics or log change.
- **Legal:** no new dependency and no licence change (libsodium on the phones, the Go standard library and `golang.org/x/crypto` in the reference, all already in use).
- **Residual risk:** the person who receives a preview can still read it; that is by design and is covered by the existing consent flow. G-07 remains required before release.

## Owner decision

**Accept or reject.** Accepting lets the agent build the Go reference with vectors, then both apps. Rejecting means the agent proposes another layout. The one open choice (keep `PROTOCOL_VERSION` 1.0 or bump to 1.1) can be answered with the decision; without an answer the CR goes ahead as written (1.0).
