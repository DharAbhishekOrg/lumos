# CR-009: Quoted replies in remote chat

- **Status:** **ACCEPTED** 2026-11-24 by the owner ("yes to all"; §6).
- **Executes:** its own slice straight after CS2c, Android then iOS. The wire
  change (Go reference, Java, Swift, vectors) lands first, in one commit.
- **Raised:** 2026-11-24 by the owner ("Shall I draft it? YES"), after CS2a
  found the gap.
- **Affected requirements:**
  - SRS-RMT-010 ("Users shall be able to reply, react, copy permitted text,
    delete locally and view timestamps"). Reply is the one part the wire
    cannot carry today.
  - SRS-UX-011 ("reply gestures");
  - SRS-RMT-011 (the AMD-005 inner event envelope);
  - TRS-PROTO-006 (unknown values fail closed);
  - TRS-CONST-003 (a register change needs an approved CR).
- **ADRs:** ADR-004 (the register is the one source). The kind table lives
  in `protocol/constants/lumos_constants.json` (`text_event_kinds`), so
  adding a kind changes `constants_hash`. Every golden vector that embeds the
  hash is regenerated, and the full conformance suite reruns in the same
  commit (TRS-CONST-003).

## 1. The gap

AMD-005's inner event envelope has four kinds: TEXT (0x00), EDIT (0x01),
DELETE_FOR_EVERYONE (0x02) and REACTION (0x03). None says "this message
answers that one", so a quoted reply cannot be sent. The screen could fake
one by pasting the quoted words into the text, but that copies the other
person's words into a new message, survives their "delete for everyone",
and shows nothing a reader can trust.

## 2. The proposal

A fifth kind, **REPLY (0x04)**: "a new text that answers an earlier message".

- **Layout:** the same as EDIT and REACTION, which already carry a target
  and a body: `kind u8 = 0x04 | target[16] | body_len u32 | body`. `target`
  is the id of the message being answered (either person's) and `body` is
  the new text, under the same limits as TEXT. Nothing about TEXT changes.
  Code 0x04 is free: 17 and 18 stay reserved for the receipt kinds (CR-005),
  and the register's note on kinds 1..3 carrying a target extends to 4.
- **It is a new message.** It gets its own id, its own ticks, and every
  action a text has. On both sides it is stored as a text with a
  `replyTo` reference.
- **The quote is never sent.** Each device draws the quoted line from its
  own copy of the target. So:
  - a reply carries no second copy of anyone's words;
  - if the target was deleted for everyone, the quote reads "Original
    message deleted";
  - if this device deleted the target for itself, or never had it, the quote
    reads "Original message not available" and the reply still shows.
- **Checks on receipt:** the target must belong to the same conversation, or
  the reply is shown without a quote. Unlike EDIT, it is never refused and
  never ignored: it is the other person's words.
- **Wire errors:** an unknown kind keeps failing closed exactly as today
  (`ERR_TEXT_UNKNOWN_EVENT_KIND`, consumed and ignored, SRS-RMT-011).

## 3. Why a new kind, not a field on TEXT

| | New kind REPLY (proposed) | Optional quote field on TEXT |
| --- | --- | --- |
| TEXT layout | Unchanged; every TEXT vector stays valid | Changes for the most common event |
| An older build | Drops the reply as an unknown kind | Refuses the TEXT (strict decoders reject trailing bytes) |
| Code | A fifth row in the kind table, the EDIT shape | A new optional field in every decoder |

Neither keeps an older build fully working, and that matters little before
the first release, because no older build exists. After release, any new
kind needs a minimum-version rule; that is TRS-PROTO-006's existing
territory, not this CR's.

## 4. Safety and privacy

- **No new data leaves the device.** A reply carries an id the peer already
  has, plus new text.
- **A "delete for everyone" stays effective:** a reply cannot preserve
  deleted words, because quotes are drawn locally from what still exists.
- **The relay sees nothing new.** The kind byte is inside the end-to-end
  encrypted plaintext.

## 5. For the owner's ruling

1. Accept REPLY (0x04) as §2 describes.
