# CR-005: A post-match RELAY_ROUTE message class, and the receipt batch size

- **Status:** **ACCEPTED** by the owner on 2026-11-23. The owner chose
  "new class via CR-005" for the route exchange over carrying it inside
  PROFILE_FULL or on the accept response, and "TRS classes 0x11/0x12" for
  receipts over hiding them inside text events.
- **Applied:** WP-05 S7e1 (this commit): register entries, the payload schema
  entry, regenerated constants in all three languages, `constants_hash` and
  every golden vector that embeds it, the consent gate on Java and Swift, and
  the route and receipt codecs with their vector families.
- **Raised:** 2026-11-23, in WP-05 S7e, by the implementing agent
  (TRS-PROTO-016: adding a message class is a protocol change;
  TRS-CONST-003: a new register value needs an approved change request).
- **Register entries (new):** `message_classes.classes[RELAY_ROUTE = 0x07]`,
  `sessions_remote_text.RECEIPT_IDS_PER_ENVELOPE`.
- **Affected requirements:** SRS-RMT-001 (remote text after leaving radio
  range needs each side's relay address), SRS-RMT-005 and SRS-RMT-014
  (delivered and read come from receipts), SRS-MAT-005/006 (post-match only),
  SRS-RMT-016 (a capability per peer, so blocking revokes exactly one),
  TRS-PROTO-005 (the class list), TRS-TRN-001 (local-only classification).
- **ADRs:** ADR-002 (the nearby session is the trust point), ADR-004 (every
  tunable value comes from the register).

## Why this is a change request

Two matched phones can only keep chatting over the relay once each knows the
other's routing id and holds a send capability the other minted for it
(WP-05 S5's capability model). Nothing in the protocol carries those today:
the TRS §9.2 class list is closed, and the post-match full-profile exchange
(PROFILE_FULL) is not built. Adding a class moves the register and
`constants_hash`, so it needs the owner's authority.

## The class

| Code | Name | Purpose |
| --- | --- | --- |
| 0x07 | RELAY_ROUTE | This device's relay address for one matched peer: its routing id and the send capability it minted for that peer |

- **Post-match only.** It joins the consent gate's MATCH_ONLY set, so it can
  neither be sent nor accepted before mutual acceptance (SRS-MAT-005/006).
- **Nearby only.** It travels inside the authenticated, encrypted nearby
  session and is not on the relay's allow-list: the relay never carries
  anyone's relay address, so it cannot be used to learn which routing ids
  talk to each other.
- **Payload** (fixed under the TRS §19 rule): `version u8 = 1 |
  routing_id[16] | capability[32]`, exactly 49 bytes. An all-zero routing id
  or capability is refused. Size bound: `transport.QR_BOOTSTRAP_MAX_BYTES`,
  like every small control class.
- Each side sends one after a match, and again whenever it re-registers (a
  new registration is a new routing id).

## Receipts on 0x11 and 0x12

No register change is needed for the classes; they exist. Their payload is
fixed here under the TRS §19 rule. A receipt is sealed in the same Double
Ratchet session as text and rides the same envelope (PREKEY until the peer
replies, then NORMAL). Its plaintext is:

`receipt_id[16] | kind u8 | count u8 | message_id[16] × count`

- `kind` is the class code (0x11 delivered, 0x12 read) and must equal the
  class the relay delivered it under; `receipt_id` must equal the relay's
  message id. A relay therefore cannot turn a "delivered" into a "read", or a
  receipt into a text, without the open failing.
- The other way round, a receipt passed off as a text message puts its kind
  byte where a text event's kind sits. Text event kinds 17 and 18 are
  therefore **reserved** in the register: the receipt decodes as an unknown
  event kind, which the text path consumes and ignores (SRS-RMT-011), so
  nothing is shown.
- `count` is 1 to `RECEIPT_IDS_PER_ENVELOPE`, so one envelope can acknowledge
  a burst of messages.
- As the owner accepted, the relay can see that an envelope is a receipt and
  which kind, but not which messages it acknowledges.

## New register value

```json
"RECEIPT_IDS_PER_ENVELOPE": {
  "default": 32, "min": 1, "max": 64, "overridable": false,
  "notes": "Message ids one delivery or read receipt may acknowledge. A wire-format bound: decoders refuse more than max, encoders send at most default.",
  "anchors": ["SRS-RMT-005", "SRS-RMT-014", "TRS-PROTO-007"],
  "source": "CR-005"
}
```

**Why 32.** A receipt with 32 ids is 16 + 2 + 512 = 530 bytes of plaintext,
comfortably inside the 1,228-byte bound for the receipt classes with the
envelope's 40-byte header, a PREKEY envelope's 172-byte prefix and the AEAD
tag. A busy conversation acknowledges a burst in one envelope instead of 32,
which also keeps receipts well inside CR-004's send rate. **Max 64** (1,042
bytes of plaintext) is the largest that still fits a PREKEY envelope under
the bound. It is not overridable because it is a wire bound both ends must
share.

## What it does not cover

- Typing indicators (0x13) remain unbuilt and out of scope.
- Rotating a capability (re-keying one peer's permission) is not needed for
  this slice: unmatch or block revokes it, and a re-registration sends a new
  RELAY_ROUTE.

## Ruling

- 2026-11-23: route exchange by a new post-match, nearby-only class via
  CR-005 (chosen over PROFILE_FULL and over the accept response); receipts on
  TRS classes 0x11/0x12 (chosen over hiding them in text events).
